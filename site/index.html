백엔드로 도메인 설계부터 API까지 구현

  • UUID는 외부 노출용, 내부 기본키는 조인용으로 분리해 사용자 수와 생성 순서 추정 방지

  • 템플릿 메서드 패턴으로 공통 검증 흐름은 부모 클래스에, 플랫폼별 값만 하위 클래스에 분리해 새 소셜 로그인을 클래스 추가만으로 지원

검색 서버 없이 자모 분해와 trigram 유사도로 음식 검색 오타 보정

  • Elasticsearch 없이 pg_trgm으로 오타 보정 검색 구현, 검색 서버 비용 절감
  • 자모 분해와 trigram 유사도로 오타가 있어도 비슷한 음식 검색
  • GIN 인덱스를 CONCURRENTLY로 생성하여 쓰기 잠금 방지, 정확 일치가 부족할 때만 유사 후보 추가

트랜잭션 분리와 CircuitBreaker로 Gemini 호출 중 DB 연결 점유 최대 3초에서 0초로 감소

  • Retry와 CircuitBreaker로 장애 차단, 장애 시 기본값 CAUTION으로 응답 유지 (회로 차단은 테스트로 확인)
  • Gemini 호출을 트랜잭션 밖으로 분리해 DB 연결 점유 방지 블로그
  • 버전 비교로 늦게 끝난 이전 분석이 최신 증상 데이터의 결과를 덮는 문제 방지

운영 중 오류모니터링을 위한 Sentry와 Better Stack 구성

  • 5xx만 Sentry로 전송하여 예외 알림 누락 해결, traceId로 요청 단위 로그 추적
  • Railway에서는 Prometheus가 앱에 접근할 수 없어, JVM 메모리, GC 지표를 30초마다 Better Stack OTLP로 전송 블로그

기획 단계부터 애자일한 프로세스로 유연한 운영, 지속적인 개선

  • 매주 스프린트 회고와 계획 회의로 우선순위를 조정
  • 출시 목표가 명확한 프로젝트로 애자일하게 진행하여 3개월 이내 App Store, Google Play 출시

AI 개발 규칙을 스킬과 훅으로 강제

  • 코드 리뷰, 보안 점검, 테스트 작성 같은 기준을 Claude Code 스킬 12개로 만들어 사용
  • Claude Code 훅 4종으로 ktlint 위반 피드백, DTO 편집은 사람 승인, 위험 명령 차단, 커밋 컨벤션 검사
  • 모든 판단을 decisions.log에 기록

기술 선택과 이유

  • Kotlin: null 안정성으로 NPE를 컴파일 단계에서 막고, sealed class로 DTO를 표현하여 분기 누락을 잡기 위해 사용했습니다.
  • Railway: 인프라 관리 부담 없이 빠르게 출시하려고 AWS, GCP 대신 PaaS를 선택했습니다.
  • Better Stack(OTLP): Railway에서는 Prometheus가 앱에 접근할 수 없어, 앱이 30초마다 지표를 보내는 push 방식으로 구성했습니다.
  • Sentry: 배포 후 발생한 예외를 로컬 재현 없이 운영 환경에서 바로 확인하기 위해 사용했습니다.
  • PostgreSQL pg_trgm: Elasticsearch 컨테이너를 따로 띄우는 비용을 아끼기 위해, 이미 쓰고 있는 PostgreSQL의 확장으로 오타 보정을 구현했습니다.

트러블슈팅 - Gemini 429가 재시도 없이 즉시 실패하던 문제

🚨 문제 상황

  • Gemini가 429(한도 초과)를 반환해도 재시도 없이 바로 실패 처리되었습니다.
  • GeminiClient의 catch-all이 5xx와 타임아웃 외 예외를 전부 null로 삼켜, Retry와 CircuitBreaker가 이를 정상 응답으로 판단했습니다.

🔧 해결 방법

  • 삼키던 예외를 전파해 Retry와 CircuitBreaker가 실패를 인식하도록 변경했습니다.
  • 재시도해도 소용없는 400, 401, 403은 재시도 대상에서 제외했습니다.

📊 개선 전후 비교

  • 이전: 429가 null로 처리되어 재시도 없이 실패했습니다.
  • 이후: 429가 재시도 대상이 되었고, 400, 401, 403은 재시도 없이 즉시 처리됩니다. 테스트도 null 반환 검증에서 예외 전파 검증으로 변경했습니다.

💡 배운 점

  • 예외를 삼키는 코드가 있으면 Retry와 CircuitBreaker가 장애를 볼 수 없다는 것을 알게 되었습니다.

  • Prometheus가 Spring Boot Actuator(JVM, GC, DB 커넥션 풀)와 Redis Exporter(캐시 hit rate, 메모리 사용량)를 수집하여 앱과 캐시 상태를 함께 확인
  • Alertmanager로 앱 다운, 5xx, p95 지연 등 알림 규칙을 정의하고 개발, 운영 환경 Discord 채널로 전송하도록 연결

  • R2 presigned URL 업로드로 파일 트래픽을 서버에서 분리하여 서버 부하 감소

  • 기록 삭제 시 AFTER_COMMIT 이벤트로 이미지와 캐시를 정리하여, 롤백됐는데 이미지만 지워지는 문제 방지 블로그

Claude Code 훅으로 Terraform 포맷 검증 자동화

  • 타 프로젝트에서 적용한 Claude Code 훅 방식을 인프라 작업에 적용
  • .tf 파일 수정 시 terraform fmt가 자동 실행되어 포맷 지적을 리뷰에서 제거

기술 선택과 이유

  • Redis ZSET: 점수 순으로 이미 정렬되어 있어 조회 시 다시 계산하거나 정렬할 필요가 없어 사용했습니다.
  • Redis: 블루그린 배포는 배포마다 컨테이너가 새로 떠서 로컬 캐시가 비게 되므로, 배포와 독립적인 Redis를 선택했습니다.
  • Terraform, Blue/Green: 콘솔 수동 관리와 재시작 중 서비스 다운타임을 없애고, 실패 시 이전 버전으로 되돌리기 위해 도입했습니다.
  • presigned URL: 업로드 트래픽과 실패 처리가 서버에 몰리지 않게 하기 위해 사용했습니다.

트러블슈팅 - 홈 화면 월별 통계 API 응답 지연

🚨 문제 상황

홈 화면 월별 통계 API에서 응답 지연이 발생했습니다.

  • 날짜별로 가장 많이 읽은 책, 읽은 시간을 조회할 때마다 GROUP BY를 다시 계산
  • EXTRACT가 걸린 컬럼이라 인덱스를 타지 못하고 풀스캔이 발생하여, 조회가 몰릴수록 응답 지연과 DB 부하가 함께 증가

🔧 해결 방법

먼저 날짜 컬럼을 분리하여 인덱스를 적용했고, 조회 시간이 약 12% 줄었지만 매번 재계산하는 구조는 그대로였습니다.

재계산 자체를 없애기 위해 Redis ZSET으로 변경했습니다.

  • 독서 기록이 끝나면 ZINCRBY로 점수를 더해 순위를 실시간 갱신
  • 조회는 ZREVRANGE로 이미 정렬된 상위 항목만 조회
  • Redis 장애 시 DB 집계로 대체

📊 개선 전후 비교

k6로 50만 건 삽입 후 부하 테스트

  • 평균 응답: 18% 감소
  • p95 응답: 20% 감소
  • 최대 응답: 77% 감소

💡 배운 점

  • 캐시는 속도 개선만을 위한 기술이 아니라, TTL과 무효화 기준, 장애 시 처리 구조까지 함께 설계해야 서비스에서 안정적으로 사용할 수 있다는 것을 알게 되었습니다.

  • JWT만으로는 로그아웃, 강제 차단, 기기 수 제한을 할 수 없어 Redis 블랙리스트와 사용자, provider, deviceId 단위 세션 관리 설계
  • 기기 수 확인과 세션 등록을 Lua Script 하나로 처리하여 동시 로그인에도 3대 제한이 어긋나지 않도록 구현 (초과 시 가장 오래된 세션 무효화)
  • 액세스 토큰에 세션 ID를 넣어, 퇴출된 세션의 토큰도 바로 차단

탈퇴 복구와 이메일 인증 흐름 보완

  • 탈퇴 유예 기간 사용자에게 복구 전용 토큰을 발급하고, 유예 판단 로직을 하나로 통합
  • 이메일 발송을 Resend로 전환하고, 비밀번호 재설정에 rate limit과 소셜 계정 분기를 추가, 소셜 계정이 함께 있을 때 나던 500 에러 수정

순번 추정을 막기 위해 외부 노출될 수 있는 PK를 TSID로 전환

  • auto-increment ID가 그대로 노출되면 전체 데이터 수와 가입과 생성 순서를 추정할 수 있어, 외부에 노출되는 ID를 TSID로 전환
  • 시간순 정렬은 유지하면서 값에 무작위 비트를 섞어 순번은 추정할 수 없도록 설계

트러블슈팅 - 전체 유저 월간 배치의 메모리 급증(OOM)

🚨 문제 상황

매월 1일 전체 유저 월간 리포트 배치에서 메모리 문제가 발생할 위험이 있었습니다.

  • findAll로 유저 전체를 한 번에 로딩하여, 유저가 늘수록 메모리에 쌓여 OOM 위험이 증가
  • 배치 하나가 실패하면 그 달 리포트 전체에 영향

🔧 해결 방법

  • Spring Batch 청크 처리로 전환하여 일정 개수씩 읽고, 청크마다 메모리를 비움 블로그
  • OFFSET 대신 키셋 페이징(user.id > :lastUserId)을 사용하여, 배치 도중 유저가 삭제되거나 변경되어도 누락 없이 조회
  • 실패를 retry(일시 오류)와 skip(잘못된 데이터)으로 나누어 하나의 오류로 배치 전체가 멈추지 않게 처리

📊 개선 전후 비교

  • 전환 전: 전월 배치가 OOM으로 실패
  • 전환 후: 다음 달 배치가 끝까지 정상 완료

💡 배운 점

  • 메모리 문제의 원인을 영속성 컨텍스트 내부 동작, 엔티티가 1차 캐시에 계속 쌓이는 구조까지 파고들게 되었습니다.
  • OFFSET은 뒤 페이지로 갈수록 비용이 커지고, 삭제 시 레코드를 건너뛸 수 있다는 것을 알게 되었습니다.
