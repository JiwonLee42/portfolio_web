What it does서비스

  • During a call, your voice and the AI’s voice are exchanged in real time.
  • The home screen shows call history and notifications, and past calls can be played back from their recordings.
  • 통화 중에는 내 목소리와 AI 목소리를 실시간으로 주고받습니다.

What I did역할

  • Built the whole calling feature on Android, as one flow: entering the call, connecting, sending and receiving audio, ending and restarting, and checking the record afterwards.
  • Managed the call session over WebSocket. No audio is sent before the server’s CALL_READY signal arrives, and the call fails if it does not come within 5 seconds.
  • Added a generation value so that late callbacks from a previous call cannot mix into a new one when the user hangs up and calls again, and changed the shutdown order so that recording resources are released only after the work has finished.
  • Handled Bluetooth and speaker output paths per Android version and device, and fell back to the default path so that the call continues when a connection fails.
  • Built the home and call history screens with MVI and Jetpack Compose, and connected recording playback and its progress with Media3.
  • As Android part lead, I tried to run the schedule and a code review culture.
  • 통화 기능을 Android에서 처음부터 끝까지 구현했습니다. 전화 진입, 연결, 오디오 송수신, 종료와 재시작, 통화 후 기록 확인까지 한 흐름으로 맡았습니다.
  • WebSocket으로 통화 세션을 관리하고, 서버의 CALL_READY 준비 신호가 오기 전에는 오디오를 보내지 않게 했습니다. 5초 안에 신호가 없으면 실패로 종료합니다.
  • 통화를 끝내고 바로 다시 걸어도 이전 통화의 지연된 콜백이 섞이지 않도록 세대 값을 두고, 녹음 자원은 작업이 끝난 뒤에 해제하도록 종료 순서를 바꿨습니다.
  • Android 버전과 기기에 따라 블루투스·스피커 출력 경로를 나눠 처리하고, 연결이 안 되면 기본 경로로 통화를 이어가게 했습니다.
  • MVI와 Jetpack Compose로 홈과 통화 이력 화면을 만들고, Media3로 녹음 재생과 진행 상태를 연결했습니다.
  • Android 파트 리드로 일정 관리와 코드 리뷰 문화 운영을 시도했습니다.

Looking back회고

  • Working on the restart race taught me that the connection state alone cannot filter out callbacks left by a previous call. Each call needs a value that tells it apart.
  • A connected WebSocket does not mean the other side is ready. Without a separate ready signal, the server can be sent data at a moment it cannot accept it.
  • For the AI summary after a call, I suggested showing a “summarizing” state first instead of polling again and again. It made me think about easing server load and improving the UX together.
  • 세션 재시작 경합을 다루면서, 연결 상태만으로는 이전 통화가 남긴 콜백을 걸러낼 수 없고 통화마다 구분되는 값이 필요하다는 걸 배웠습니다.
  • WebSocket은 연결됐다고 해서 상대가 받을 준비까지 된 게 아니라서, 별도의 준비 완료 신호가 없으면 서버가 받을 수 없는 시점에 데이터를 보낼 수 있다는 걸 배웠습니다.
  • 통화 종료 후 AI 요약은 계속 물어보는 폴링보다 요약 중 상태를 먼저 보여주는 UX를 제안했고, 서버 부하도 줄이고 UX도 개선하는 방식에 대해 생각해 보게 됐습니다.

Building a real-time voice call as one session flow

AI와의 실시간 음성 통화를 한 세션의 흐름으로 구현

I split the call into connecting, getting ready, sending and receiving, ending and restarting, and checking the record afterwards, and guarded each stage against the problems it can cause.

AI와의 실시간 음성 통화를 연결, 준비, 송수신, 종료와 재시작, 통화 후 기록 확인까지 한 세션의 흐름으로 나눠 구현하고, 단계마다 생길 수 있는 문제를 막은 경험입니다.

Requirements요구사항

  • Real-time, both ways: voice must go back and forth with the AI character without breaking up.
  • Session lifetime: connecting, getting ready, sending and receiving, ending and restarting have to hold together inside one call.
  • Device differences: the call has to work whichever input and output path the speaker, Bluetooth or Android version gives.
  • After the call: the history has to be visible on the home screen, and the recording has to be playable again.
  • 실시간 양방향: AI 캐릭터와 음성을 서로 끊김 없이 주고받아야 합니다.
  • 세션 수명 관리: 연결, 준비, 송수신, 종료, 재시작이 하나의 통화 안에서 이어져야 합니다.
  • 기기 환경 대응: 스피커, 블루투스, Android 버전에 따라 입력·출력 경로가 달라도 통화가 되어야 합니다.
  • 통화 이후: 통화가 끝난 뒤에도 홈에서 이력을 확인하고 녹음을 다시 들을 수 있어야 합니다.

Problem문제

What goes wrong if it is done the simple way

단순하게 구현할 경우 발생할 수 있는 문제

  • Sending before ready: if microphone audio is sent as soon as the socket connects, the server takes the noise before it is ready for the user cutting in, and the AI voice breaks off.
  • Interference from the previous call: when a call ends and a new one starts right away, delayed callbacks from the old session can touch the state of the new one.
  • Racing on resources: releasing a recorder or player while it is still working can touch a resource that is already released.
  • Output differs by device: if Bluetooth fails to connect or the permission is missing, the call itself may not work.
  • 준비 전 송신: 연결되자마자 마이크 오디오를 보내면, 서버가 준비 전 잡음을 사용자의 끼어들기로 오인해 AI 음성이 끊깁니다.
  • 이전 통화의 간섭: 통화를 끝내고 바로 새로 걸면, 이전 세션의 지연된 콜백이 새 세션 상태를 건드릴 수 있습니다.
  • 자원 해제 경합: 녹음이나 재생이 진행 중인데 자원을 바로 해제하면, 이미 해제된 자원에 접근할 수 있습니다.
  • 기기별 출력 차이: 블루투스 연결이 실패하거나 권한이 없을 때 통화 자체가 안 될 수 있습니다.

Approach해결

One call as one flow

통화 한 건의 흐름으로 나눠서 해결

  1. Enter the call and connectThe connection and the session are managed in the call repository, over an OkHttp WebSocket.
  2. Wait for CALL_READY, 5 second timeoutA 5 second timer starts when the socket connects. Captured PCM is thrown away until the server’s CALL_READY arrives. If it does not arrive in time, the call fails with READY_TIMEOUT and the connection is closed. The point is to treat “connected” and “the server is ready to receive” as two different moments.
  3. Send and receive PCM both waysAudio captured with AudioRecord is sent, and audio from the server is played with AudioTrack.
  4. End the callShutdown runs as stop, wait for the capture job to finish, then release. Calling again raises the generation value and the flow starts again from the connection.
  5. Check the record afterwardsThe home screen shows call history and notifications, and the record detail plays the recording with Media3 while keeping the progress in step with the screen.
  1. 전화 진입, WebSocket 연결OkHttp WebSocket 연결과 세션을 통화 Repository에서 관리합니다.
  2. CALL_READY 대기, 5초 타임아웃연결 성공 시점부터 5초 타이머를 걸고, 서버의 CALL_READY를 받기 전에는 캡처된 PCM을 버립니다. 5초 안에 못 받으면 READY_TIMEOUT으로 실패 처리하고 연결을 종료합니다. 연결됐다는 것과 서버가 받을 준비가 됐다는 것을 다른 시점으로 본 것이 핵심입니다.
  3. PCM 양방향 송수신AudioRecord로 캡처한 PCM을 전송하고, 서버에서 받은 오디오는 AudioTrack으로 재생합니다.
  4. 종료종료는 stop, 캡처 job 종료 대기, release 순서로 진행합니다. 다시 걸면 세대 값이 올라가고 연결부터 다시 시작합니다.
  5. 통화 후 기록 확인홈에서 통화 이력과 알림을 보여주고, 기록 상세에서 Media3로 녹음을 재생하면서 진행 상태를 화면과 맞춥니다.

While sending송수신 중

Two things handled during the call

통화 중에 함께 처리한 것

  • Sound processing: input is taken as VOICE_COMMUNICATION, with an echo canceler and a noise suppressor on devices that support them. Audio focus and call mode are managed together.
  • Output path: Android 12 and above use the communication device selection API. Lower versions use an asynchronous SCO connection and a BroadcastReceiver. Without the permission or the device, the call falls back to the default path, so a Bluetooth failure does not become a call failure.
  • 음향 처리: 입력은 VOICE_COMMUNICATION으로 받고, 지원하는 기기에서는 에코 캔슬러와 노이즈 서프레서를 적용합니다. 오디오 포커스와 통화 모드도 함께 관리합니다.
  • 출력 경로 분기: Android 12 이상은 통신 장치 선택 API를, 그보다 낮은 버전은 비동기 SCO 연결과 BroadcastReceiver를 사용합니다. 권한이나 기기가 없으면 기본 경로로 넘어가서, 블루투스 실패가 통화 실패로 이어지지 않게 합니다.

Ending and restarting종료와 재시작

  • The socket and the recorder carry a generation value, so callbacks from a previous session ignore themselves.
  • Shutdown is split into stop, waiting for the capture job to finish, and release, so that the blocking read() and the release do not collide.
  • Concurrent access to AudioTrack on the playback side is also blocked.
  • 소켓과 레코더에 세대 값을 둬 이전 세션의 콜백이 스스로 무시되게 합니다.
  • 종료는 stop, 캡처 job 종료 대기, release 순서로 나눠 블로킹 read()와 해제가 부딪히지 않게 합니다.
  • 재생 쪽 AudioTrack의 동시 접근도 막습니다.
