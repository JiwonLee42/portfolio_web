Looking back회고

  • Using a TSID lowers how predictable an ID exposed outside the system is. I learned that an identifier design can be a security requirement.
  • With a Lua script, checking and applying can be one atomic operation, which removes race conditions such as the concurrent-login limit.
  • Diagnosing a failure from thread dumps showed me the risk of naive implementations like findAll, and that team conventions survive only when they are documented.
  • TSID로 외부 노출 ID의 예측 가능성을 줄이며, 식별자 설계도 보안 요구사항이 될 수 있다는 걸 배웠습니다.
  • Lua Script로 확인·반영을 하나의 원자 연산으로 묶어 동시 로그인 제한 같은 경합 문제를 없애는 방법을 익혔습니다.
  • 스레드 덤프 기반 장애 진단으로 findAll 같은 단순 구현의 위험을 확인하고, 팀 컨벤션은 문서화해야 실제로 유지된다는 걸 배웠습니다.

Removing the out-of-memory risk of the monthly report with Spring Batch

전체 유저 배치의 OOM 위험을 Spring Batch로 해결

I replaced a findAll that loaded every user at once with chunk processing and keyset paging.

findAll로 인한 배치 OOM 위험을 Spring Batch 청크 처리와 키셋 페이징으로 해결한 경험입니다.

Requirements요구사항

  • On the first of every month, generate a monthly report for all users.
  • Even as users grow, the batch must run to the end without memory problems.
  • If a user is deleted or changed during the batch, no data may be missed.
  • 매월 1일 전체 유저를 대상으로 월간 Report를 생성해야 합니다.
  • 유저 수가 늘어나도 배치가 메모리 문제 없이 끝까지 돌아야 합니다.
  • 배치 도중 유저가 삭제·변경돼도 데이터가 누락되지 않아야 합니다.

Problem문제

  • The monthly batch loaded all users at once with findAll, so memory kept accumulating as users grew and the risk of an out-of-memory error kept rising.
  • The query also read everything in one go, so a single failed batch would affect the whole month's report.
  • 매월 전체 유저 Report 배치가 findAll로 유저 전체를 한 번에 로딩해, 유저가 늘수록 메모리에 계속 쌓여 OOM 위험이 커졌습니다.
  • 조회 자체도 전체를 한 번에 읽는 구조라, 배치 하나가 실패하면 그 달 전체 Report에 영향을 줬습니다.

Approach해결

  • Chunk processing: Spring Batch reads a fixed number of users at a time and frees the memory after each chunk.
  • Keyset paging: the reader continues with user.id > :lastUserId instead of OFFSET, so it picks up where it left off without gaps even if users are deleted or changed midway.
  • Retry and skip: a failure is either retried (a temporary error) or skipped (bad data), so a single error does not stop the whole batch.
  • 청크 처리: Spring Batch 청크 처리로 전환해, 일정 개수씩 나눠 읽고 청크가 끝날 때마다 메모리를 비웁니다.
  • 키셋 페이징: Reader 조회는 OFFSET 대신 키셋 페이징(user.id > :lastUserId)으로 해, 유저가 중간에 삭제·변경돼도 누락 없이 이어서 조회합니다.
  • retry·skip: 실패는 retry(일시 오류)와 skip(잘못된 데이터)으로 나눠, 하나의 오류로 배치 전체가 멈추지 않게 했습니다.

Why not OFFSETOFFSET이 아닌 이유

  • OFFSET gets more expensive on later pages because it has to skip everything before them. And if a user is deleted during the batch, the values shift and records can be skipped.
  • Keyset paging only reads rows after the last processed ID, so deletes and changes do not disturb which rows come next.
  • OFFSET은 뒤 페이지로 갈수록 앞부분을 건너뛰는 비용이 커지고, 배치 도중 유저가 삭제되면 값이 밀려 레코드를 건너뛸 수 있습니다.
  • 키셋 페이징은 마지막 처리 ID보다 큰 데이터만 이어서 조회하므로, 삭제·변경에도 다음 대상을 안정적으로 가져옵니다.

Result결과와 배운 점

  • The previous month's batch failed with an out-of-memory error. After the change, the next month's batch ran to the end normally.
  • I went deeper into why memory piled up: how transactions and the persistence context work inside, where entities keep accumulating in the first-level cache.
  • 전월 배치는 OOM으로 실패했고, 전환을 적용한 다음 달 배치는 끝까지 정상 완료됐습니다.
  • 메모리 문제의 원인을 트랜잭션·영속성 컨텍스트의 내부 동작 방식, 즉 엔티티가 1차 캐시에 계속 쌓이는 구조까지 깊게 생각해 보게 됐습니다.
