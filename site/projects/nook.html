What it does서비스

  • Search for books and add them to a bookshelf. Read in focused sessions and see reading stats on the home screen.
  • Write reading logs for each book on the shelf and view them as a timeline.
  • The backend is fully implemented, and the service is deployed and under continuous QA.
  • 책을 검색하고 서재에 추가하며, 집중 독서와 홈 화면 독서 통계를 조회할 수 있음.
  • 서재에 담은 책의 독서 기록을 작성하고 타임라인으로 조회할 수 있음.
  • 백엔드는 구현을 마쳤고, 배포 후 지속적으로 QA 중임.

Speeding up the monthly stats API on the home screen

홈 화면 월별 통계 API 속도 개선

I stopped re-aggregating on every read and cached the aggregate itself in a Redis sorted set.

홈 화면 월별 통계 API의 반복 집계 비용을 캐싱과 인덱싱으로 줄인 경험임.

Requirements요구사항

  • The home screen shows stats as a calendar, such as the most-read book of each day and the time read per book. It is a low-write, high-read screen, so responses must be fast.
  • Even when reads pile up, database load must not keep growing.
  • With containers replaced on every deploy, including blue/green, an empty cache right after a deploy must not send a surge of load to the database.
  • 홈 화면은 달력 형태로 통계를 보여 주는 API를 쓰는데, 날짜별 가장 많이 읽은 책, 책 읽은 시간 통계는 조회가 잦은 화면이라 응답이 빨라야 함.
  • 조회가 몰려도 DB 부하가 계속 커지면 안 됨.
  • 배포마다 컨테이너가 새로 뜨는 블루그린 환경에서도, 배포 직후 캐시가 비어 부하가 몰리는 일이 없어야 함.

Before기존 방식

A GROUP BY recomputed on every read

조회할 때마다 GROUP BY로 재계산

  • Each request ran a plain aggregate query. EXTRACT on a date column stopped the index from being used and forced a full scan, so more reads meant slower responses and more database load together.
  • Splitting the date column and adding an index cut query time by about 12%. But the structure that recomputes on every read stayed, so the root problem, load growing with reads, was still there.
  • 홈 화면 통계를 조회할 때마다 DB에서 GROUP BY를 매번 다시 계산하는 단순 집계 조회 방식이었음. EXTRACT 함수가 걸린 컬럼이라 인덱스를 타지 못하고 풀스캔까지 겹쳐, 조회가 몰리면 응답 지연과 DB 부하가 함께 커짐.
  • 날짜 컬럼을 분리해 인덱스를 타도록 고쳤고 실제로 조회 시간이 약 12% 줄었음. 하지만 조회할 때마다 매번 재계산하는 구조 자체는 그대로라, 조회가 몰릴수록 부하가 계속 늘어나는 근본 문제는 남아 있었음.

Approach해결

Change the structure so nothing is recomputed

Redis ZSET으로 재계산 자체를 하지 않는 구조로 변경

  1. A reading log endsThe book's score is added with ZINCRBY, so the ranking is updated in real time.
  2. The home screen is openedZREVRANGE returns the top few from an order that is already sorted.
  3. If Redis is downThe request falls back to the GROUP BY query on the database.
  1. 독서 기록이 끝나면ZINCRBY로 해당 책의 점수를 더해 순위를 실시간으로 갱신함.
  2. 홈 화면을 조회하면ZREVRANGE로 이미 정렬돼 있는 순서에서 상위 몇 개만 바로 꺼냄.
  3. Redis 장애 시DB에서 GROUP BY 연산을 실행하는 경로로 대체함.
  • “The most-read book of a day” is hot data at a point in time that is read again and again. So instead of recomputing on each read, the aggregate result itself is cached.
  • A sorted set always keeps its members ordered by score, so there is nothing to re-sort or recalculate at read time.
  • 날짜별 가장 많이 읽은 책의 통계는 특정 시점의 인기 데이터가 반복 조회되는 패턴이라, 매번 재계산하는 대신 집계 결과 자체를 Redis ZSET에 캐싱함.
  • ZSET은 항상 score 순 정렬을 유지하는 자료구조라 조회 시점에 다시 정렬하거나 계산할 필요가 없음.

캐시는 속도 개선만을 위한 기술이 아니라, TTL, 무효화 기준과 장애 시 내부 처리 구조까지 함께 설계해야 실제 서비스에 쓸 수 있다는 걸 배움.

Zero-downtime deploys and monitoring on Terraform

Terraform 기반 무중단 배포·모니터링 구축

I turned infrastructure that was managed by hand in the console into code, then built zero-downtime deploys and warning-signal monitoring on top of it.

콘솔로 수동 관리하던 인프라를 Terraform으로 코드화하고, 그 위에 무중단 배포와 위험 신호 기반 모니터링 구조를 구축한 경험임.

Before기존 방식

  • Infrastructure: values were looked up and typed in by hand in the AWS console. Development convenience and production control were mixed together.
  • Deploys: git pull and restart the application. The service was down during the restart, and there was no automated way back after a failure.
  • Monitoring: none. When something went wrong in operation, there was no way to notice it.
  • 인프라: AWS 콘솔에서 값을 직접 조회해 입력하는 수동 관리 방식이라, 개발 편의와 운영 통제가 같은 방식으로 섞여 있었음.
  • 배포: git pull 후 애플리케이션을 재시작하는 방식이라 재시작 동안 서비스가 중단됐고, 실패 시 되돌리는 절차도 자동화돼 있지 않았음.
  • 모니터링: 관측 자체가 구축돼 있지 않아, 운영 중 이상이 생겨도 알아챌 방법이 없었음.

Infrastructure as codeIaC 도입

  • An EC2 Terraform module: to fix the manual console management, I wrote a module that manages the security group, IAM role, EC2 instance and EIP, with the VPC and subnet passed in as variables from the existing network. The development server that already existed was brought in with import.
  • One module, staged rollout: the same module is meant for the development, production and monitoring servers. Development is applied and used freely for inspection and reproduction; production and monitoring have a Terraform plan ready, with secrets and the deploy steps to be controlled separately once they are applied.
  • EC2 Terraform 모듈: 콘솔 수동 관리를 고치기 위해, 보안 그룹, IAM 역할, EC2, EIP를 관리하는 모듈을 작성하고 VPC, 서브넷은 기존 네트워크를 변수로 받게 함. 기존에 배포해 둔 개발 서버는 import로 편입함.
  • 단계적 적용: 같은 모듈을 개발계, 운영계, 모니터링 서버에 쓰도록 설계함. 개발계는 적용해 자유롭게 확인, 재현하고 있고, 운영계, 모니터링은 plan까지 작성해 둔 상태로, 적용 시 시크릿 관리와 배포 절차를 별도로 통제할 계획임.

Blue/green deploy블루그린 배포

Two containers of the same app, and Nginx only switches traffic

동일 애플리케이션을 blue/green 두 컨테이너로 운영하고 Nginx는 트래픽 전환만 담당

  1. GitHub Actions builds the imageIt is pushed to ECR.
  2. The new version starts on the idle containerThe container that is serving traffic is left untouched.
  3. Health checkTraffic is passed over only after the new container is healthy.
  4. Nginx switches the upstreamIf the new version fails, the old one keeps serving and the deploy rolls back automatically.
  1. GitHub Actions가 이미지를 빌드ECR에 올림.
  2. 유휴 컨테이너에 신버전을 먼저 띄움서비스 중인 컨테이너는 건드리지 않음.
  3. 헬스체크통과 후에만 트래픽을 넘김.
  4. Nginx upstream 전환실패하면 기존 버전이 그대로 서비스를 유지하고 자동 롤백됨.

Monitoring모니터링

A monitoring server, separate from development and production

모니터링 서버를 운영, 개발 서버와 별도로 구축

  • Logs from each server are collected by Grafana Alloy, sent to Loki, and viewed in Grafana by the environment label (dev or prod).
  • Prometheus scrapes Spring Boot Actuator (JVM memory and GC, database connection pool) and Redis Exporter (cache hit rate and memory usage), so application state and cache state are observed together.
  • 각 서버의 로그를 Grafana Alloy로 수집해 Loki로 연결하고, Grafana에서 environment(dev/prod) 라벨별로 조회할 수 있게 구성함.
  • Prometheus가 Spring Boot Actuator(JVM 메모리, GC, DB 커넥션 풀 지표)와 Redis Exporter(캐시 hit rate, 메모리 사용량)를 각각 스크래핑해, 애플리케이션 상태와 캐시 상태를 함께 관측함.

Alerts알림 연동

  1. PrometheusCollects metrics from the development and production servers, split by the environment label.
  2. Alert rulesApp is down, 5xx ratio above 5%, or p95 response time above 1 second, evaluated per environment.
  3. Alertmanager to DiscordIt matches the same label and posts to separate development and production channels.
  1. Prometheus개발, 운영 서버의 지표를 environment 라벨로 구분해 수집함.
  2. 알림 규칙앱 다운, 5xx 비율 5% 초과, p95 응답 1초 초과 등을 environment별로 집계해 정의함.
  3. Alertmanager에서 Discord로이 라벨로 매칭해 개발용과 운영용 Discord 채널로 나눠 전송함.
